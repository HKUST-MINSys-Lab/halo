## 1. Findings that change what the next runs mean

**N1 - P1. No stored manifest can be regenerated by the current code.** `_stable_choice` was
rewritten from `rng.choice(values, size, replace=False)` to rejection sampling for speed. Same
seed, same pool, different rows: for one (cell, k, query, label) the old draw is
`[3956, 2033, 1760, ...]` and the new draw is `[1762, 4685, 2349, ...]`. Rebuilding scenario 1,
`motionsense/phone_front_pocket`, 8 s, k=8 and comparing with the stored
`scenarios_full_20260916/manifests.jsonl`: **0 of 3,693 plans have the same support rows**.
`manifest_fingerprint` was also re-encoded (JSON to `struct`), so fingerprints cannot even be
compared across versions, and the protocol tag written by `_run_provenance` is still
`deployment-scenarios-v2-20260915`. `build_manifest` (the sealed k-curve) uses the same helper, so
every `sealed_*` result and every `episode_manifests.json` is affected too. Consequences:

- every table produced so far (`scenarios_full_20260916`, `scenarios_curriculum12_20260916`,
  `scenarios_neighbors_precurriculum_20260916`, `scenarios_baselines_equal_fusion_k0_64_20260916`,
  all `sealed_*`) sits on episodes the repository no longer generates;
- the first sweep's §0 table (promoted classifier vs Stage A on byte-identical manifests) cannot be
  extended to Stage B or to any new checkpoint without re-scoring the promoted checkpoint as well;
- the design documents' "immutable episode manifests" statement is true only within one code
  version, which nothing records.

Either revert `_stable_choice` to the NumPy path, or bump the protocol tag, re-run everything and
say so in the journal. Doing neither leaves the results directory internally inconsistent.

**N2 - P1 (fairness). The baseline headline readout was switched to equal-weight fusion with 1-NN
hidden by default, and the only measurement available says the switch hurts one baseline.**
`run_scenarios.score_task` and `sealed_eval.main` now give external encoders only
`equal-weight-normalized-fusion` unless `--readouts`/`--baseline-diagnostic-readouts` is passed; the
1-NN/prototype/ridge rows become `diagnostic_only` and are excluded from `RESULTS.md`. The only
artifacts with both rows for the same cells are scenario 1 at 8 s, k in {1..64}
(`scenarios_baselines_equal_fusion_k0_64_20260916`), split=all:

| model | fusion minus 1-NN, macro-F1 points | cells | cells where fusion is worse |
|---|---:|---:|---:|
| HARNet | +12.3 | 25 | 0% |
| UniMTS | +6.9 | 25 | 8% |
| LiMU-BERT-X | +4.7 | 21 | 33% |
| NormWear | **-6.2** | 25 | **88%** |

Scenario 1 is the case where fusion has a structural advantage (half the truths are unenrolled,
so 1-NN cannot name them), and NormWear still loses six points because its semantic term is
noise. For the complete-enrollment scenarios the only evidence is this sweep's smoke (§6,
HARNet5, 4 s, k=1, the model with the largest scenario-1 gain from fusion), macro-F1, split=all:

| cell | 1-NN | fusion |
|---|---:|---:|
| s2 RealWorld waist <- waist, same subject (matched control) | 11.1 | 3.1 |
| s2 RealWorld waist <- forearm, same subject | 8.4 | 2.8 |
| s3 MotionSense <- Shoaib | 46.4 | 50.0 |
| s4 MotionSense query accel-only | 45.9 | 49.4 |
| s5 MotionSense query at 20 Hz | 45.5 | 51.8 |
| s6 MM-Fit left wrist | 26.7 | 19.6 |
| s7 RealWorld composite <- single (matched control) | 35.3 | 33.2 |
| s7 RealWorld composite <- single | 28.9 | 32.6 |

Fusion is below 1-NN in four of the eight cells, by up to eight points, for the baseline that
benefits most from it elsewhere. A second effect shows in the paired deltas of the same smoke:
the scenario-minus-control delta for s7 is -6.5 under 1-NN and -0.6 under fusion, and for s5 it
is -0.4 under 1-NN and +2.3 under fusion. The semantic term is untouched by the perturbation, so
fusion dilutes the encoder's degradation and makes a baseline look more robust to the scenario
than its representation is. Meanwhile HALO's combiner is learned (`lambda(k)` / the gate), so the
default comparison is "learned combiner versus fixed combiner" with the baseline's best untrained
readout suppressed, and with severity curves that understate baseline degradation. The
implementation document's sentence "no baseline is handicapped" is contradicted by these numbers.
Before any table leaves the repository, keep the baseline 1-NN row beside the fusion row in every
enrolled cell (also for the severity deltas), or define the baseline row as the better of the two
per cell and say so.

**N3 - P1. The Stage B run trained on the old sampler.** The log of

**N4 - P2. No checkpoint written before today can be resumed.** `main()` copies

## 2. Does the curriculum imitate the scenarios? (measured on the real train split)

Probe: 120 batches of 4 support sets (480 sets, 1,830 episodes) drawn with the trainer's exact
`draw_kwargs` from `support_corpus_from_index` (196,712 windows, 31 streams, 26 keys).

| scenario | training analogue | delivered? | measurement |
|---|---|---|---|
| s1 partial enrolment | enrolment regime `partial` (0.25) | yes | 115/480 sets partial; P(truth enrolled) 0.507 vs mean coverage 0.511, so hiding is independent of the truth |
| s2 cross placement, same dataset | acquisition regime `cross_placement` (0.25) | **not as scored** | share 0.293 of enrolled sets, but 99.7% of cross-placement episodes carry at least one support row from *another dataset* and 64.8% carry only other-dataset rows (`_keys_for` ignores dataset). 62% of cross-placement queries come from WISDM, HARMES and HHAR, whose only partners are other datasets; 24% are the HARMES/WISDM wrist pair (C11). 67% of cross-placement queries are `walking`, `standing`, `sitting`, `drinking`, `brushing_teeth`. The only phone pair is HHAR waist <-> WISDM right pocket; the sealed s2 cells (RealWorld waist/forearm/thigh, Shoaib pockets/belt/wrist) have no within-dataset phone analogue in training |
| s3 cross dataset, shared labels | acquisition regime `cross_dataset` (0.25) | **body-IMU only** | share 0.106; eligible query datasets are exactly dsads, forth_trace and xrf_v2 (wrist keys shared three ways, right thigh shared with RealDisp); viable labels dsads 2, realdisp 1, xrf_v2 4, forth_trace 5. No phone or watch key is shared by two training datasets (HHAR and KU-HAR differ in gravity state; WISDM pocket is unique; the two wrist watches differ in site string). Every sealed s3 cell is phone-phone or watch-watch |
| s4 missing modality | gyro dropout p=0.20 per recording (Stage B) | yes | 18.1% of 1,500 items tagged; 2% of those are inert (accel-only HHAR stream); query, support and both cases arise because recordings are perturbed independently |
| s5 rate mismatch | anti-aliased resample p=0.25 to U(15, 100) Hz (Stage B) | yes, but mostly the easy direction | 24.3% of items tagged; **68% are upsampled** (hardware rates 20-51 Hz vs a 15-100 Hz draw), so only about 8% of all recordings lose bandwidth. Sealed s5 targets 20 and 25 Hz for 50 Hz phones (bandwidth loss) plus 100 Hz. `channel_source_rates` stays at the hardware rate for every upsampled item (checked on all 365) |
| s6 new domain | zero-support regime only | partial | label novelty is not modelled beyond k=0 |
| s7 device set | multi-device composition p=0.5, query and support composed independently | yes | 444/1,500 items multi-device; rate/modality draws replay identically across devices (one rate per composite; checked on 58 composites) |
| s8 cold start | intersection of the above | as good as its parts | - |

Two structural conclusions. First, the mismatch half of the curriculum is really one regime,
"other dataset, possibly other site, body-IMU or a single phone/watch pair", at about 40% of
enrolled sets, and it never contains the device families the evaluator scores under s2/s3.
Second, the rate curriculum teaches interpolation invariance far more than bandwidth loss.
Neither is a bug in the sampler; both are properties of the eight-source corpus that the design
document should state instead of the 0.50/0.25/0.25 target.

## 3. Evaluator findings (beyond §0)

**N5 - P2. Asymmetric row sets by construction.** In every enrolled task HALO gets 1-NN,
prototype, ridge and the classifier; baselines get fusion only; HALO gets a fusion row only in
coverage tasks. The `SUMMARY.md` generator and the paired-delta tracker key on `(model, readout)`,
so no delta compares HALO's floor with a baseline's floor unless `--readouts` is passed. This is
the mechanism behind N2; the primary comparison must be stated as classifier-vs-fusion or the
default readout set must be symmetric.

**N6 - P2. One unloadable stream still aborts a whole scenario cell.** `build_tasks` runs under a
single `try` in `main`; s2 to s8 iterate several datasets inside it, so a missing grid or a
converter error for one dataset produces a `build_tasks` failure for the entire (scenario, k,
window). s5 isolates only the `derive_resampled` step.

**N7 - P3. Rate perturbation edge handling differs between training and evaluation.**
`derive_resampled` calls `resample_poly(..., padtype="line")`; the trainer's `_rate` uses the
default constant padding. Both are anti-aliased polyphase; the boundary samples differ. Not a
correctness issue, but the two are documented as the same transform.

**N8 - P3. `_halo_residual_predictions` reloads the checkpoint per task**; with the default full
grid (8 scenarios x 3 windows x 8 k values x up to 20 tasks) that is thousands of `torch.load`s.

**N9 - P3. `run_scenarios` default grid.** `--k` now defaults to `0 1 2 4 8 16 32 64` and
`--window-seconds` to `4 8 16` (the implementation document was updated to match). The
zero-support bank is built once per (provider, window) and cached; grids exist at all three
durations for all eight training datasets, so this is cost, not correctness.

## 4. Trainer and Stage B findings (beyond §0)

**N10 - P2 (telemetry). Validation silently drops the gate's support-count and sensor-margin
weights.** `weighted_present_metrics` weights any `scenario/*/{loss,accuracy,semantic_weight}` key
by its sibling `.../fraction`; `scenario/support_count/*/semantic_weight` and
`scenario/sensor_margin/*/semantic_weight` have no sibling, get weight 0 and are omitted. Probe:
`weighted_present_metrics([{"scenario/support_count/0/semantic_weight": 1.0, ...}], [4])` returns
neither key. The Stage B log has them only because it ran older code. The design document's
acceptance telemetry ("split by support count and sensor-evidence margin") is therefore absent
from validation rows under the current code.

**N11 - P3 (telemetry). The per-episode `*_support` perturbation flags are uninformative.**
`run_step` marks the support side perturbed if *any* of its ~54 support windows was; the Stage B
log shows `rate_resampled_support/fraction` 0.729 and `modality_dropped_support/fraction` 0.724,
which is simply P(k is not 1). The `recording_fraction` keys (0.252, 0.200) are the honest ones.

**N12 - P3 (provenance). Stage B is not Stage A plus perturbations episode-for-episode.**
`item_with_rng` now draws a replay seed *before* the multi-device decision, so the device subsets
differ from Stage A for the same `data_seed` even with both probabilities at zero.

**N13 - P3.** `--val-repeats-per-dataset` is validated and never read; `--val-episodes` help text
says "eight per eligible held-out dataset" while the default is a flat 64 support sets.
`shrunk` now means "fewer rows than C x k", so partial and unequal-count episodes count as shrunk
(the two run logs still show 0.0 because they used the old sampler).

**N14 - P3.** `support_per_candidate` and `sampler/k_*_support_set_fraction` still report the
pre-downsample k (C13c); the realized per-candidate maximum matched it in 461/480 sets in the
probe, so the distortion is small.

## 5. Verified correct (with the measurement)

- Sampler leakage over 1,830 episodes: 0 support rows from the query's execution; 0 cross-subject
  violations; 0 same-subject violations; cross-dataset purity 1.000; compatible key-equality 1.000.
- Every support set's queries share one acquisition key (0/480 violations), which is the C1 fix.
- Zero-support sets are `not_applicable` (149/149); enrolment shares 0.45/0.24/0.31 of sets.
- k is drawn uniformly over feasible values (2:76, 4:69, 1:60, 8:52, 16:43, 32:31 of 331).
- Feasibility index 3.2 s once; 60 ms per batch afterwards.
- Augmentation: `phase_a(rate_p, channel_dropout_p)` enables exactly those two transforms
  (summary printed and checked); realized 0.243 / 0.181; replay is bit-identical for the same
  step seed; validation uses the plain (unaugmented) path; `source_rate <= min(hardware, achieved)`
  held on every perturbed item.
- Adaptive gate under `torch.autocast(bfloat16)` on the GPU: lambda finite, float32, nonzero
  gradient in `lambda_table`, both LayerNorm parameters and all four gate weights/biases (closes
  the first sweep's open GPU item).
- Evaluator: `derive_accel_only` masks and zeroes; `derive_resampled` keeps the effective source
  rate at min(source, target) and errors on non-finite output; cross manifests exclude the query's
  execution within a dataset and never claim identity across datasets; `equal_weight_normalized_fusion`
  refuses non-uniform support widths and mismatched score matrices; `classwise_neighbor_scores`
  is exact on both CPU and GPU paths; s1 coverage cells are k-invariant by construction.
